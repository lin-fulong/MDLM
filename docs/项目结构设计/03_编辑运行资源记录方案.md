# 编辑运行资源记录方案

状态：已接入编辑运行。本文只约定编辑运行的资源记录；评价运行的指标与输出不在本次范围内。

## 目标与统计口径

每次 `main.py` 编辑运行生成一份便于 Excel、WPS 和 pandas 查看、筛选的 CSV，覆盖四项数据：总体用时、实际进入编辑的源案例数量、每个源案例的编辑用时、整次运行的峰值显存。

当前 `MDLM/runner.py` 将同一 `source_case_id` 的所选事实放在一轮联合编辑。因此 CSV 的“样本”是**一个源案例编辑轮次**，不是单条事实；即使某轮被编辑器拒绝，这轮也计入已执行样本。一个源案例含多个事实时，不拆分或平均分摊该轮时间。

`total_samples` 统计**实际开始**的轮次数：正常完成时等于 `run_report.json` 的 `case_count`；中途失败时只包含已开始的轮次，包括当前失败轮次。`run_report.json` 中的 `case_count` 仍表示筛选后的计划轮次数。保留 `status` 列，以区分完整结果和中途失败的结果。

总体用时从创建 `runs/<run_id>/` 并开始执行编辑后计时，到算法执行、模型产物保存和必要的上下文清理结束；最终 CSV 与报告自身的写入时间不纳入。单样本用时从该轮权重快照前开始，到编辑、该轮产物保存和独立模式权重恢复后结束；若该轮失败，记录到失败和恢复处理结束时已耗的时间。使用单调时钟 `time.perf_counter()`，在 CUDA 计时边界同步设备，结果以秒保留三位小数。总用时包含数据准备、模型加载、各轮编辑和最终产物保存，因此通常大于各轮用时之和。

`peak_vram_gib` 只在总行填写：在整个编辑运行开始前重置 PyTorch CUDA 峰值统计，结束时读取各设备的 `max_memory_reserved`，换算为 GiB（`1024 ** 3` 字节）。多卡时取各设备峰值的最大值，表示**单张卡上观测到的最高峰值**，不把不同卡的峰值相加。CPU 运行时留空。该值是本进程 PyTorch 分配器保留显存的峰值，不代表整张显卡的总占用，也不包含其他进程或 PyTorch 分配器之外的显存。只重置一次峰值统计，不在案例间重置，以保证总峰值覆盖模型加载和全部轮次。

## 输出位置

以编辑输出目录 `output = <output_root>/<run_id>` 为基准，在本次实验目录下建立 `result/`：

```text
<output_root>/<run_id>/result/resource_report.csv
```

默认配置下的示例：

```text
MDLM/
├── runs/smoke_001/run_report.json
├── runs/smoke_001/result/resource_report.csv
└── logs/mdlm/LLaDA-8B-Instruct/cases/...
```

`<output_root>/<run_id>` 已按现有运行机制逐次隔离，因此每次运行的资源 CSV 与该次实验的 `run_report.json` 和模型产物放在一起。报告中记录最终 CSV 的绝对路径 `resource_csv_file`，便于定位；自定义 `output_root` 时仍使用同一层级结构。

## CSV 字段与示例

固定五列，顺序如下：

| 列 | `total` 行 | 源案例行 |
| --- | --- | --- |
| `item` | `total` | `source_case_id` |
| `status` | `complete` / `failed` | `complete` / `failed` |
| `total_samples` | 实际开始的源案例轮次数 | 留空 |
| `elapsed_seconds` | 总体用时 | 本轮用时 |
| `peak_vram_gib` | 整次运行的单卡峰值 | 留空 |

```csv
item,status,total_samples,elapsed_seconds,peak_vram_gib
total,complete,2,145.382,22.170
cf_00001,complete,,67.340,
cf_00002,complete,,73.180,
```

首行固定为 `total`，其后按数据集实际编辑顺序每个源案例一行。`complete` 表示该轮算法已结束，包含接受和拒绝两种决策；具体决策继续从 `run_report.json` 读取。CSV 使用标准库 `csv` 正确转义案例 ID，UTF-8 BOM 编码兼容常见表格软件，数值列保持可直接计算的数字文本。

异常时也写出正式 CSV：总行标记 `failed`，列出所有已完成轮次，并给当前已开始而未完成的轮次一行 `failed`。若失败发生在第一轮之前，`total_samples` 为 `0`，没有案例行。失败原因保留在现有 `run_report.json` 和 `.log`，不增加 CSV 列。若进程被强制终止或机器断电，Python 的 `finally` 无法保证执行；运行期间每完成一轮就原子更新同目录的 `resource_report.partial.csv` 快照，供恢复检查。正常或捕获到失败时写出正式 CSV 并清理快照。

## 实现位置与验收

1. 在 `util/resource_usage.py` 加入轻量计时和 CUDA 峰值读取工具，保持 CPU 路径不触发 CUDA 调用；监测代码不改模型权重、随机数或算法计算。
2. 在 `MDLM/runner.py` 的运行外层和源案例循环接入计时；在已有 `finally` 中汇总成功或失败的记录，并写出 CSV。失败时资源读取尽力而为，不让监测异常覆盖原算法异常。
3. 在 `util/experiment_log.py` 附加总用时、样本数、峰值显存和 CSV 路径的简短摘要；在 `run_report.json` 写入 `resource_csv_file`，保持现有评价读取所需字段不变。
4. 在 `README.md` 说明路径、字段和“样本”的分组口径；`runs/*` 已由 `.gitignore` 忽略。
5. 用现有 CPU 小模型端到端测试核对总行、每轮行、样本数、顺序、独立/连续模式和失败落盘；在 CUDA 单案例运行中核对峰值非空、模型加载期被计入、CSV 与报告状态一致。

验收条件：正常运行有且仅有一份正式 CSV，首行总览、每轮一行；总行的 `total_samples` 与实际开始的轮次数一致；失败运行保留已完成及当前失败轮次；CPU 的显存列为空；CUDA 总峰值覆盖完整编辑执行期；现有编辑决策和评价产物读取不受影响。
