# 01 项目结构设计

状态：项目结构已落地，代码文件均为空占位文件。本文是对[《扩散知识编辑算法开发方案 V1.0》](../扩散知识编辑算法开发方案%20V1.0.md)的目录设计；数学和阶段门槛以[《最终逻辑 V1.0》](../最终逻辑%20V1.0.md)及开发方案为准。目录和空文件的存在不代表代码已经实现。

## 1. 结构目标与参考

[MEMIT 官方仓库](https://github.com/kmeng01/memit)把算法、数据、实验、超参数和工具分开，并让[实验入口](https://github.com/kmeng01/memit/blob/main/experiments/evaluate.py)调用[算法实现](https://github.com/kmeng01/memit/blob/main/memit/memit_main.py)。本项目参考这种清晰的职责划分，再按实际主算法增加去噪状态、矩阵提取、联合残差优化、验收回退与独立生成评价。MEMIT 的自回归输入和具体更新公式不能直接替代本项目的扩散模型逻辑。

根目录下的 `MDLM/` 承载主要算法逻辑与编辑流程入口；`model/` 管理原始模型及适配代码，`data/` 管理数据集及读取代码，`util/` 统一放状态和矩阵提取入口。`evaluation/` 与 `tests/` 目前仅预留空目录。一次运行的中间产物和最终结果统一归入 `runs/`。配置集中放在 `configs/`，不再为每种配置单建目录。

## 2. 拟建项目目录树

根目录本身名为 `MDLM`，下列同名 `MDLM/` 是其中的 Python 算法包。模型名、数据集名均为占位符，等选定实际资产后再命名。

```text
MDLM/                                      # 项目根目录
├── README.md                              # 项目说明与运行顺序
├── requirement.txt                        # 依赖清单，按用户指定文件名
├── .gitignore                             # 忽略模型权重、数据与运行产物等
├── configs/                               # 各阶段配置，按文件名区分用途
├── MDLM/                                  # 主要算法逻辑包
│   ├── __init__.py
│   ├── contracts.py                        # 配置、产物结构与不变量
│   ├── states.py                           # 兼容状态、监督权重与 F
│   ├── writeback.py                        # H 求解、固定 Q 与诊断
│   ├── candidate.py                        # 全调用位置的 R(Qk) 前向
│   ├── optimize.py                         # J(R)、多层联合优化
│   ├── merge.py                            # ΔW=RQ、实际合并与等价核验
│   ├── acceptance.py                       # 开发三门槛、试步与回退
│   └── workflow.py                         # 单轮主流程；可选刷新编排
├── model/                                 # 原始模型及其调用方式
│   ├── __init__.py
│   ├── base.py                             # 模型适配接口
│   ├── registry.py                         # 选择具体模型适配器
│   ├── adapters/                          # 每个原始模型的调用脚本
│   │   └── <model_name>.py                 # 加载、tokenizer、去噪、模块定位
│   └── models/                            # 原始模型权重/配置/tokenizer
│       └── <model_name>/                  # 可为本地目录或外部路径引用
├── data/                                  # 数据集与对应读取脚本
│   ├── __init__.py
│   ├── schema.py                           # 统一案例与用途字段
│   ├── readers/                           # 每个数据集的读取/转换脚本
│   │   └── <dataset_name>.py
│   ├── validation/                        # 真值、对齐、切分与泄漏检查
│   └── datasets/                          # 实际数据资产
│       └── <dataset_name>/
│           ├── raw/                       # 原始文件，不覆盖
│           ├── processed/                 # 规范化案例、token 档案
│           └── splits/                    # train/dev/test 与用途清单
├── util/                                  # 真实模型状态/矩阵提取脚本
│   ├── collect_denoise_states.py          # 自主采样与完整状态保存
│   ├── filter_compatible_states.py        # 调用 MDLM.states 的筛选规则
│   ├── extract_reference_keys.py          # 提取各层 K
│   ├── extract_keep_statistics.py         # 提取各层 C
│   └── validate_matrix_artifacts.py       # 重放、形状、数值与清单 QA
├── evaluation/                            # 当前为空，预留独立评估空间
├── tests/                                 # 当前为空，预留验证空间
├── docs/                                  # 现有研究文档和本结构文档
│   └── 项目结构设计/01_项目结构设计.md
└── runs/                                  # 每次运行的状态、矩阵、模型与评价结果
```

树中明确命名的 Python 文件已创建为 0 字节占位文件，后续按开发顺序实现。`evaluation/`、`tests/` 保持空目录，里面没有文件或子目录。`model/models/` 已存在且目前为空，未来用于放原始模型；若权重位于其他磁盘，由配置指向该位置。`data/datasets/` 存放数据文件，`data/readers/` 放对应的读取/转换代码，两者分别对应 `model/models/` 与 `model/adapters/`。`<model_name>`、`<dataset_name>` 和 `<run_id>` 是命名示意，不作为字面目录创建。

## 3. 各目录的唯一职责

| 目录 | 放什么 | 边界 |
| --- | --- | --- |
| `MDLM/` | 算法公式、状态监督、$Q$ 求解、$R$ 优化、权重合并、验收流程 | 不保存原始权重或原始数据；不直接调用外部裁判 |
| `model/models/` | 原始模型权重、Tokenizer 与原模型配置，或其受控路径说明 | 不放编辑后的模型；不提交大权重 |
| `model/adapters/` | 每个原始模型的加载、编码、mask、去噪、logit 位置和目标模块定位 | 对外统一适配接口；不实现编辑目标 |
| `data/datasets/` | 来源可追溯的原始数据、处理版和划分 | 原始文件不覆盖；训练、开发、测试用途分开 |
| `data/readers/`、`data/validation/` | 数据集特定解析、规范化与质量检查 | 不暗中把缺失真值填成目标新答案 |
| `util/` | 与模型交互的状态采集、$K/C$ 提取及质量报告脚本 | 不求 $R$，不修改模型权重；$Q$ 属于算法求解 |
| `evaluation/` | 当前只保留空目录；为后续独立评估实现预留位置 | 此阶段不放文件或子目录；裁判不进入训练梯度 |
| `tests/` | 当前只保留空目录；为后续验证工作预留位置 | 此阶段不放文件或子目录 |
| `configs/` | 模型、数据、提取、编辑和评价配置 | 使用清晰文件名区分，不存密钥或机器私有路径 |
| `runs/` | 冻结配置、固定状态、$K/C/Q$、QA、$R$ 检查点、接受/回退、生成与评价结果 | 按运行和轮次隔离，保留失败记录，不覆盖旧运行 |

`MDLM/`、`model/`、`data/` 在实现时作为 Python 包；`util/` 放提取阶段命令入口。编辑阶段由 `MDLM/workflow.py` 编排，不需要另设一层薄命令脚本。`MDLM` 使用大写包名，后续导入时保持大小写一致。项目根目录与包目录同名，运行命令从项目根目录或安装环境执行，避免依赖临时修改 `sys.path`。

## 4. `MDLM/` 算法包内部划分

`MDLM/` 内不再创建子文件夹。首版用以下同级文件表达算法步骤；若某文件以后确实过大，再依据实际维护需要拆分。

```text
MDLM/
├── __init__.py
├── contracts.py                         # 配置、产物引用、形状/有限性约束
├── states.py                            # 公式（1）～（3），兼容筛选与 F
├── writeback.py                         # 公式（6）～（9），H X=K、Q=Xᵀ
├── candidate.py                         # 公式（11），真实多层候选前向
├── optimize.py                          # 公式（10）（12），J(R) 与 R 优化
├── merge.py                             # 公式（13）～（15），实际 ΔW 和合并
├── acceptance.py                        # 公式（16）～（18），三门槛与回退
└── workflow.py                          # 串接已验收产物与单轮主算法
```

`contracts.py` 只定义共享结构与不变量，`workflow.py` 只控制阶段顺序；数学实现在各自文件中。`writeback.py` 的 $Q$ 是给定 $K,C,\lambda$ 的固定写回因子，`optimize.py` 的 $R$ 是随后在真实候选模型上优化的变量。`acceptance.py` 中 $G_{\mathrm{dev}}$ 与 $U$ 始终以最初模型 $\theta_0/W_0$ 为参照。

## 5. 从提取到评估的依赖与开发顺序

```text
configs + model + data
           ↓
util：采集完整状态 → 筛选兼容状态 → 提取 K、C → QA
           ↓（产物通过、基准/事实顺序一致）
MDLM.writeback：求解 Q
           ↓
MDLM.candidate + MDLM.optimize：真实候选前向、J(R)、联合优化 R
           ↓
MDLM.merge + MDLM.acceptance：ΔW=RQ、合并、公共试步、验收/回退
           ↓
evaluation：固定最终模型的独立自由生成与裁判
```

| 阶段 | 主要归属 | 输入与可检查输出 |
| --- | --- | --- |
| P0 | `model/`、`data/`、`configs/` | 原始模型适配、真实 tokenizer/位置对齐、案例用途清单 |
| P1 | `util/collect_denoise_states.py`、`util/filter_compatible_states.py`、`MDLM/states.py` | 完整自主状态、兼容状态、固定监督权重 |
| P2 | `util/extract_reference_keys.py`、`util/extract_keep_statistics.py`、`util/validate_matrix_artifacts.py` | 同轮同基准的 $K,C$ 与 QA 报告；这是算法开发前的阶段门槛 |
| P3 | `MDLM/writeback.py`，由 `MDLM/workflow.py` 调用 | $Q$、线性求解残差和数值报告 |
| P4 | `MDLM/candidate.py`、`MDLM/optimize.py`，由 `MDLM/workflow.py` 调用 | 合格 $R^*$ 或明确失败记录 |
| P5 | `MDLM/merge.py`、`MDLM/acceptance.py`，由 `MDLM/workflow.py` 调用 | 接受的实际模型或恢复基准的回退记录 |
| P6 | `evaluation/`（当前预留为空） | 后续独立生成、裁判与覆盖率报告 |

运行方式保持单一：P0 从 `data/` 的读取与校验接口准备案例；P1/P2 从 `util/` 启动状态及矩阵提取，其中 `filter_compatible_states.py` 调用 `MDLM.states` 的唯一筛选实现；P3～P5 由 `MDLM/workflow.py` 调用同级算法模块。`workflow.py` 负责读配置、核验上游产物、记录结果和回退，不复制算法公式。P1/P2 提取完成且通过 QA 前，不启动真实编辑主流程。

## 6. 运行产物与配置约定

```text
runs/<run_id>/
├── config.lock.*                       # 本次运行的冻结配置
├── round_<n>/
│   ├── manifest.json                   # 模型、数据、基准和事实顺序摘要
│   ├── states/                         # 完整输入、兼容/冲突诊断
│   ├── matrices/                       # 按层保存 K、C、Q
│   ├── qa/                             # 提取、重放和求解检查
│   └── editing/                        # R 检查点、α 试步及验收记录
├── final_model/                        # 已接受模型或可核验的增量引用
├── generations/                        # 独立输入及完整回答
├── judgments/                          # 裁判原始和结构化结果
└── reports/                            # 指标、失败与覆盖率
```

每个矩阵保存层名、维度、dtype、事实列序、模型修订、本轮基准摘要、统计配方及校验和；`K`、`C`、`Q` 通过同一轮清单关联，不能只按文件名配对。第二轮刷新须创建新 `round_<n>` 并重新采集状态、$K,C,Q$；$\theta_0/W_0$ 引用保持不变。`data/datasets/<name>/raw/` 始终保留原始快照；处理数据和切分要有版本。`runs/` 下的子目录由实际运行按需生成，目前不预建。

`requirement.txt` 使用既定文件名，未来安装命令为 `pip install -r requirement.txt`。依赖版本在真实环境确认后固定。`.gitignore` 覆盖模型权重、原始/处理数据的大文件、`runs/`、缓存、环境目录和密钥文件；小型配置模板、示例数据、文档和测试样例仍可纳入版本控制。

## 7. 验证与后续扩展

`tests/` 现在保持空目录。进入实现和验证阶段后，再决定如何放置状态筛选、矩阵求解、梯度、真实模型捕获、合并一致性及信息隔离等检查；当前结构不预设 `unit/`、`integration/`、`numerical/` 子目录。真实模型实验结果单独进入 `runs/`。

首版只为实际需要的原始模型和数据集增加对应脚本，不创建空的模型/数据集子目录作为假支持。以后加入其他编辑基线，可增设 `baselines/`；它应共用 `data/` 的用途划分及 `evaluation/` 的独立评价口径。当前 `docs/算法逻辑/`、`docs/算法计划文档/` 等现有文档保持原位。
